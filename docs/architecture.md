# Architecture

## Note representation

I use a shared event format: MIDI pitch, start time in seconds, duration in seconds, and optional confidence. MIDI confidence is 1. Audio confidence is median pYIN voiced probability near an onset. It is not a calibrated pitch-correctness probability.

The reference also carries measure numbers and start/end times from pretty_midi's downbeats. Its tempo map and time signatures determine those boundaries. Missing time signatures use 4/4 with a warning. JSON capture can send those same boundaries for a custom reference.

## Input pipeline

MIDI files go through pretty_midi. I combine non-drum instruments and sort simultaneous notes by pitch. Live MIDI uses browser note-on and note-off messages and sends validated events to `/api/capture`.

Audio is loaded as mono at 22,050 Hz. librosa detects onsets, then pYIN estimates one fundamental pitch per frame. I take the median pitch and voiced probability in the early part of each onset segment. The tracker uses 4,096-sample frames and 512-sample hops. A spectral check looks for strong peaks outside the tracked fundamental's harmonics, or several peaks with almost no energy at the supposed fundamental. If at least 25% of sampled active frames look suspicious, I hide the scores and warn about overlapping sound. This threshold is a heuristic and does not prove that a recording is monophonic.

Browser recording uses AudioWorklet and writes mono PCM WAV, avoiding a WebM decoder dependency. Permission requests have a timeout. Late microphone approvals after timeout close their streams. Recordings stop at 119 seconds. MIDI capture caps events at 600, separates inputs/channels, closes held notes on stop, and detaches event handlers.

## Why a DTW-related alignment

DTW follows a low-cost path through two sequences that progress at different speeds. That is useful when a player slows down or speeds up. But unrestricted DTW can reuse a note in several matches, which makes missed/extra accounting unclear.

I kept the same dynamic-programming idea but use one-to-one diagonal matches and explicit insert/delete steps. A match costs `min(0.65 * pitch_difference, 1.5) + min(time_difference / 0.3, 2)`. A gap costs 1.2. The pitch cost cap helps keep an isolated wrong pitch as one mismatch instead of turning it into both a missed and an extra note. A sufficiently large timing difference can still favor gaps.

I start with endpoint timing normalization, align, then fit timing from matching pitches with adequate confidence. Median pairwise slopes and a median intercept reduce sensitivity to a few bad notes. With at least 12 matches I consider a quadratic curve if it reduces median residual by at least 35% and stays monotonic with bounded slopes. I repeat the align/fit cycle three times, then score local residuals. Gradual drift is removed; a short local delay should remain.

This is not unrestricted DTW, and I do not claim it handles every tempo change. Repeated patterns, sparse takes, and poor initial matches can select the wrong path. Each sequence is limited to 600 notes; alignment time/memory are O(NM).

## Report

The report contains note pairs, raw and aligned played times, separate pitch/timing statuses, extra notes, per-bar error summaries, confidence, warnings, and recommendation provenance. The README defines the score formulas. Audio suspicion hides all three scores instead of presenting unreliable numbers.

The UI shows scores and counts first, then a note timeline, reference/performance piano roll, measure heatmap, note table, and recommendations. Dark mode persists locally. The saved demo is generated by the same Python code and checked for equality in a regression test.

## API and request handling

| Route | What it does |
| --- | --- |
| `GET /api/health` | Reports service and recommender setting |
| `GET /api/demo` | Computes the synthetic report and recommendations |
| `GET /api/reference` | Returns the demo reference and bars |
| `POST /api/reference` | Parses a custom reference for keyboard capture |
| `POST /api/analyze` | Accepts a MIDI reference and MIDI/audio take |
| `POST /api/capture` | Accepts validated JSON events and optional bars |

A request-size middleware checks declared and streamed body size before multipart parsing. Defaults are 22 MB per request and 20 MB per file. Private temporary directories avoid trusting filenames. They are removed before model recommendations run. Numerical work runs in a worker thread. There is no durable background-job queue.

## Recommenders

`RECOMMENDER=rules` returns 3 to 5 deterministic bar-specific exercises. `ollama` calls `/api/generate` on a local service with a JSON schema. `api` calls hosted Chat Completions only with a configured key. Both receive a compact summary of at most eight bars, not files or full notes.

Pydantic checks the returned shape, lengths, number of suggestions, and fields. Bar references must occur in the sent summary. Invalid responses, HTTP failures, and 20-second timeouts retain rules and set a visible notice. The hosted API has an in-memory per-socket-IP limit. It does not trust arbitrary forwarded IP headers. Rules do not use the network even if a key is present.

## Quick demo

`demo_server.py` uses only Python's standard library to serve the committed build and `demo/report.json`. It returns a clear error for real upload requests. `tools/update_demo.py` copies the current frontend build and Python report into that folder. This keeps the two-minute presentation path separate from scientific dependency installation.
